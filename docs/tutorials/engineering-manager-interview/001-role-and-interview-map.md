# Role and Interview Map

The manager's product is a team that repeatedly delivers safe outcomes. That requires technical judgment, people
development, execution, hiring, stakeholder alignment, and operational ownership.

## Accountability map

```text
direction        capability        execution          operation
priorities  -->  hiring/coaching -> flow/quality  --> SLO/incidents
     |                 |                |                  |
     +------------- architecture and risk ---------------+
```

You do not need to be the deepest specialist in every area. You must create a decision process that surfaces the right
facts, involves the right experts, records trade-offs, and produces accountable follow-through.

## Typical interview dimensions

| Dimension          | What strong evidence demonstrates                                                 |
| ------------------ | --------------------------------------------------------------------------------- |
| System design      | requirements, trade-offs, reliability, migration, operability, communication      |
| Technical judgment | quality bar, delegation, architecture review, debt decisions, learning            |
| Execution          | scope, dependencies, risk, forecast, incremental delivery, stakeholder choices    |
| People             | clear feedback, coaching, performance, growth, conflict, inclusion                |
| Hiring             | role definition, structured evidence, calibration, onboarding, capacity           |
| Operations         | preparation, incident roles, decisions under uncertainty, learning and prevention |
| Leadership         | direction, influence, difficult trade-offs, ownership, measurable outcomes        |

## Manager-altitude answer

An IC-only answer says, "I rewrote the slow query." A manager answer may include that technical insight, but explains:

- how impact and urgency were established;
- who owned diagnosis and what support they needed;
- how risk and alternatives were reviewed;
- which guardrail prevented recurrence;
- how the engineer or team became more capable;
- which outcome changed.

Avoid claiming team work as personal heroics. Use "I" for your decisions and actions, "we" for team execution, and name
contributions when possible.

## Evidence standard

Good stories include a baseline and an outcome: p99 latency, incident frequency, escaped defects, deployment lead time,
on-call load, hiring funnel quality, retention, delivery confidence, or demonstrated skill growth. State when evidence
is qualitative; do not invent precision.

## Checkpoint

Write one example for each dimension with your action, the mechanism it changed, and the measured result. If one story
must cover every dimension, the portfolio is too narrow.
