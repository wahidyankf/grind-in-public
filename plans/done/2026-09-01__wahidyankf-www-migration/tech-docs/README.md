# Technical Design

## Context

This is the first TypeScript project in this repository. `tsconfig.base.json` exists but nothing consumes it, `libs/` holds only a README, and the TypeScript requirements in `testing-policy/tooling.md` have never been executed. Every conformance decision here therefore sets a precedent rather than following one, which is why the fallback path is written down instead of left to judgment.

The source application is a static Next 16 site with no database, no backend, and no network dependency at runtime. Its whole surface is four routes, a 544-line CV record, a personal-projects list, a client-side search over both, and a PDF export.

## Architecture

```text
specs/apps/wahidyankf-www/behavior/*.feature  <- canonical corpus: 12 features, 55 scenarios
                    |
     +--------------+------------------+-------------------------+
     |                                 |                         |
tests/bdd/                     tests/integration/       apps/wahidyankf-www-e2e/
12 files: 11 Gherkin           cv-export.feature        steps/*.steps.ts
bindings + 1 wrapper           only: 2 scenarios        8 files: 36 scenarios bound,
contract test                                           19 unbindable here
     |                                 |                         |
vitest-cucumber, jsdom         vitest, node env         playwright-bdd, chromium
over src/**                    real filesystem:         next start -> real browser
53 scenarios                   CV record, PDF output
```

The corpus is discovered by both adapters from one path. Nx inputs on every affected target list `"default"` first and then `{workspaceRoot}/specs/apps/wahidyankf-www/behavior/**/*.feature`, so adding, editing, renaming, or deleting a feature invalidates the targets that must revalidate it, and so does an edit to the project's own files. `"default"` is named rather than assumed because a target-level `inputs` array replaces Nx's default input set instead of extending it, so an array holding the corpus glob alone would hash the corpus and nothing else. This mirrors what `badakmini-cli` already does for Go, with the same `behavior` spelling and the same target names.

## Selected Decisions

**No new validation tooling.** `ose-public` enforces corpus-to-binding completeness with `rhino-cli`, an F# program invoked through `dotnet run`. That does not come, so what replaces it has to be stated precisely rather than assumed.

Inside a feature file that a binding loads, `@amiceli/vitest-cucumber` fails the run on a scenario the binding does not implement, a missing or mistyped step, and a missing Scenario Outline variable. That is the undefined-step half of the validator, and it is genuinely covered.

Within a loaded feature it also throws `FeatureUknowScenarioError` for a binding declared against a scenario the file does not contain, so the mapping is checked in both directions there.

Two things it does not do. It cannot see a feature file that no binding loads at all, because nothing then executes to notice; Phase 3 closes that with a counted check that eleven of the twelve files are loaded by exactly one binding under `tests/bdd/` and the twelfth, `cv-export.feature`, by the integration test alone. And it does not report a step definition that no scenario uses. That half is given up deliberately, and recording it here is the honest form, because a silently missing check is worse than a stated gap. If it later proves to matter, it becomes a Badak Mini subcommand in its own plan.

**Corpus layout is flattened.** `ose-public` nests by domain and area: `specs/apps/wahidyankf/behavior/wahidyankf-www/gherkin/<area>/<name>.feature`. This repository nests by project and nothing else: `specs/apps/badakmini-cli/behavior/<name>.feature`. All nine app feature filenames are unique across their areas, so that part of the flattening is a pure move with no rename and no collision.

**The loader corpus comes with the loader.** Inlining `ts-env-loader` moves its behavior into this application, so the two feature files under `specs/libs/ts-env-loader/behavior/gherkin/` come too: `env-loader.feature` lands as `behavior/tier-env-loading.feature` and `port-resolver.feature` lands unchanged. That is 13 more scenarios, bringing the ported corpus to 11 features and 53 scenarios, and the delivered corpus to 12 and 55 once `cv-export.feature` is authored in Phase 3. One rename is forced: the app corpus already carries a feature titled `APP_ENV tier env-file loading`, so the ported file's title becomes `Tier env-file loader module`. Leaving the loader's scenarios behind would inline code whose only executable specification stayed in another repository.

**Three libraries, four components.** `wahidyankf-www` consumes exactly four symbols from `web-ui` — `ScrollToTop`, `ThemeToggle`, `SearchComponent`, and `HighlightText`. `web-ui`'s `cn` helper does not come with them: none of the four imports it, and the application already owns an identical `cn` at `src/features/app-shell/core/style.ts` with `style.unit.test.ts` covering it, so porting `libs/web-ui/src/utils/cn.ts` would add a second copy of one function and a second test for it to the 99% denominator. `web-ui-token` reaches the application only as two CSS imports, `tokens.css` and `wahidyankf.css`; the TypeScript token modules are unused. Inlining is therefore four source files and two stylesheets, not a design system. The `@source "../../../../libs/web-ui/src/**/*.{ts,tsx}"` directive in `globals.css` exists only to make Tailwind scan the external library, so it is deleted rather than repointed: inlined components already sit inside the default scan root.

**The environment loader keeps `dotenv`, at an exact pin.** `ts-env-loader` uses `dotenv` to read one `.env.<tier>` file, and the inlined loader keeps that call rather than reaching for Node's `process.loadEnvFile`. The [dependency selection policy](../../../../repo-governance/development/dependency-selection-policy.md) requires the requirement, the rejected built-in alternative, and the evidence to be recorded, so all three are here.

The requirement is loading one tier file into an **injectable** `EnvRecord` — `loadTierEnv({ env })` writes into the record it is handed, defaulting to `process.env` — **without erroring when the file is absent**, which is loader rule 4 and the normal CI case.

The rejected alternative is `process.loadEnvFile`. It fails that requirement twice, verified against Node 24.16, the version this repository targets. First, it takes a path and nothing else: `process.loadEnvFile.length` is 0 and its only optional parameter is the path, so it always writes into the real `process.env` and there is no target record to inject — which is exactly what the ported `env-loader.feature` scenarios do. Second, it throws `ENOENT` on a missing file rather than returning quietly, so rule 4 would have to be re-implemented around it in a `try`/`catch` that also has to distinguish a missing file from a malformed one. `dotenv.config({ processEnv, override: false })` satisfies both directly: `override: false` is rule 3 ("process environment wins"), and `configDotenv` catches the read failure internally and reports it only on the returned `.error` field, which is rule 4.

The remaining evidence the policy asks for is the same as for every other arriving package: `dotenv` is running this exact loader in `ose-public` at the recorded source commit, on the same Node 24 toolchain. The pin is `16.4.7`, the version `ose-public` pins today. The inlined loader therefore keeps all five original loader rules unchanged — tier selection through `APP_ENV`, exactly one file, process environment wins, absence is not an error, and the stray-file guard against Next's auto-loaded `.env`, `.env.production`, and `.env.local`.

**Filenames conform.** The [code style policy](../../../../repo-governance/development/code-style-policy.md) requires descriptive lower-hyphenated TypeScript filenames. Six ported files are PascalCase. Five are renamed in the move — `Navigation.tsx` and its co-located `Navigation.unit.test.tsx`, `CvContent.tsx`, `HomeContent.tsx`, and `PersonalProjectsContent.tsx` — and the sixth, `SearchSection.tsx`, is removed instead because nothing imports it.

The rename touches far more than the six files. Thirty-one references name one of these modules by path: seventeen in `src/`, and fourteen more inside the nine step files, which arrive later in Phase 3 and which no rename item can reach before they land. The owner's APFS volume is case-insensitive, so every stale path still resolves locally after the rename and the whole set breaks only on the Linux CI runner — and a `vi.mock` whose path no longer resolves mocks nothing and silently renders the real component. `delivery.md` therefore inventories both sets by file and repoints the step-file set in Bind the Corpus rather than in Port the Source.

**Nx targets use the `command` shorthand.** Every ported target is an `nx:run-commands` block with an `options` object. The [Nx workspace policy](../../../../repo-governance/development/nx-workspace-policy.md) requires the `command` shorthand for a single-command target and reserves `nx:run-commands` with an explicit `options.commands` list and `parallel` set to `false` for ordered aggregates. Three targets are aggregates: `test:quick`, `test:coverage`, and `lint`, the last because `tooling.md` requires both Biome and a commentary check and they run in order. Every other target owns one command. `test:specs` disappears with `rhino-cli`.

## Dependencies

Twenty-nine npm packages arrive with the two ported manifests. That is the union of both manifests — thirty-two entries — less the two `@open-sharia-enterprise/*` specifiers, which this plan removes, and `typescript`, which both manifests pin and both entries are deleted in favour of the root pin. Six more are added at the root — five in Phase 1, and `@typescript-eslint/parser` **added during execution** in Phase 3, when `lint:commentary` turned out to have no reader for TypeScript or JSX; its requirement is a parser ESLint can hand TypeScript and JSX sources to, its rejected alternative is dropping the commentary check, which the plan's own fallback item ruled out on the evidence, and the evidence is 39 parse errors across 25 files that the parser resolved to zero. One more, `dotenv`, is added to the application manifest in Phase 3. Two of the twenty-nine — `react-icons` and `class-variance-authority` — are removed again later in Phase 3 for having no importer, so thirty-four packages are delivered by this plan — 25 in `apps/wahidyankf-www/package.json`, 3 in `apps/wahidyankf-www-e2e/package.json`, and the 6 it adds at the root, which already carried 6 others it does not touch. Every one of those numbers is countable from the delivered manifests, from the table below, or from the execution note above it.

That is a larger dependency intake than anything this repository has taken on, so the [dependency selection policy](../../../../repo-governance/development/dependency-selection-policy.md) requires the requirement, the rejected built-in alternative, and the evidence to be written down rather than inherited by copying a manifest.

The shared evidence for every arriving package is that it is already running the same application in `ose-public` at the recorded source commit, on Next 16, React 19, and Node 24 — the same toolchain this repository targets. That is what the policy asks for: current evidence from the project itself of active maintenance and compatibility, rather than a reputation. Every version is exact-pinned; five caret ranges in the application manifest and one in the E2E manifest are pinned during the port.

## Target Contract

The project exposes the target names `badakmini-cli` exposes, so `npm run test:unit`, `npm run test:coverage`, and the pre-push affected run reach it without special-casing.

| Target | Command shape | `cwd` | Cached | `outputs` |
| --- | --- | --- | --- | --- |
| `build` | `next build` | `{projectRoot}` | yes | `{projectRoot}/.next` |
| `dev` and `start` | `node ../../scripts/next-with-port.mjs <mode> --env WAHIDYANKF_WWW_PORT --default 3201` | `{projectRoot}` | no | none |
| `typecheck` | `tsc --noEmit` | `{projectRoot}` | yes | none |
| `lint` | ordered aggregate of `lint:biome` then `lint:commentary` | none | yes | none |
| `lint:biome` | `biome check` — a linter only, because the root `biome.json` sets `formatter.enabled` and `assist.enabled` to `false` | `{projectRoot}` | yes | none |
| `lint:commentary` | `eslint --config eslint.config.mjs src` | `{projectRoot}` | yes | none |
| `test:unit` | `vitest run --project unit` | `{projectRoot}` | yes | none |
| `test:integration` | `vitest run --project integration` | `{projectRoot}` | no | none |
| `test:coverage:unit` | `vitest run --project unit --project behavior --coverage --coverage.thresholds.lines=99` | `{projectRoot}` | yes | `{projectRoot}/coverage` |
| `test:coverage:integration` | `vitest run --project integration --coverage --coverage.include='src/features/cv/**/pdf.ts' --coverage.thresholds.lines=99` | `{projectRoot}` | no | `{projectRoot}/coverage` |
| `test:coverage:behavior` | `vitest run --project behavior` | `{projectRoot}` | no | none |
| `test:coverage` | ordered aggregate of the three coverage targets above | none | yes | none |
| `static-routes:validation` | `nx run wahidyankf-www:build --skip-nx-cache && node apps/wahidyankf-www/scripts/validate-static-routes.mjs` | `{workspaceRoot}` | no | none |
| `test:quick` | ordered aggregate of `typecheck`, `lint`, `test:unit`, `test:coverage:unit`, `test:coverage:behavior`, with `dependsOn` naming `static-routes:validation` | none | yes | none |
| `generate:cv-pdf` | `npx tsx scripts/generate-cv-pdf.ts` | `{projectRoot}` | no | `{projectRoot}/public/wahidyankf-kresna-fridayoka-cv.pdf` |

The `cwd` column is part of the contract, not incidental. Every single-command target runs from `{projectRoot}`, which is what makes `next build`, `tsc --noEmit`, `biome check`, and the project-relative `../../scripts/next-with-port.mjs` path resolve at all. `static-routes:validation` is the one exception and runs from `{workspaceRoot}`, because its command invokes `nx run` and then names `apps/wahidyankf-www/scripts/validate-static-routes.mjs` from the root. The three ordered aggregates need no `cwd`: every entry in their `options.commands` is an `npm exec nx -- run` invocation that resolves from wherever it starts. Declaring a working directory does not force a target out of the `command` shorthand — Nx merges the shorthand into whatever `options` the target already has, so `command` and `options.cwd` coexist — and the shorthand is what the [Nx workspace policy](../../../../repo-governance/development/nx-workspace-policy.md) requires of a single-command target.

The `outputs` column exists because a cached target that declares none is a trap: Nx replays the cache hit, restores nothing, and reports success. `build` is where that bites — with an unchanged input set the replay leaves no `.next`, and the `next start` behind the E2E suite then fails on a run that said it passed. `{projectRoot}/.next` for `build` and the generated PDF path for `generate:cv-pdf` are what the source `project.json` declares at the recorded commit; `{projectRoot}/coverage` is what it declares on the single `test:coverage` target this plan splits into three. `typecheck` declares none deliberately: the `tsconfig.tsbuildinfo` it writes is TypeScript's own incremental cache rather than an artifact a dependent task reads.

`test:quick` deliberately stops short of the `test:coverage` aggregate, invoking `test:coverage:unit` and `test:coverage:behavior` directly instead. That is exactly the shape `badakmini-cli` uses, and the shape [workspace commands](../../../../repo-governance/development/workspace-commands.md#build-and-test) describes as the quick gate: type-check, lint, unit test, unit coverage, then behavior completeness. Reaching `test:coverage` would pull `test:coverage:integration` in behind it, and pre-push runs `test:quick` for every affected project, so every push touching this application would write PDFs to the real filesystem.

`test:coverage:unit` runs the `behavior` project as well as `unit`, because `src/features/env/core/tier-env.ts` and `port-resolver.ts` are exercised only by their Gherkin bindings under `tests/bdd/`. Against a whole-`src/**` denominator a unit-only run would report both at zero. `badakmini-cli` resolves the same problem the same way: its `test:coverage:unit` passes `./tests/bdd` alongside `./tests/unit`.

`test:e2e` belongs to `apps/wahidyankf-www-e2e`, which declares `implicitDependencies` naming `wahidyankf-www` and `dependsOn` naming `wahidyankf-www:build`. `implicitDependencies` shapes the project graph and the affected calculation; it does not order tasks, and the `webServer` block runs `next start`, which needs a `.next` directory it will not build. The owning application defines no `test:e2e` target at all. An `echo` placeholder is precisely the failure mode the [testing policy](../../../../repo-governance/development/testing-policy.md) names, so absence is the correct signal.

That dedicated project exists under the [BDD policy](../../../../repo-governance/development/behavior-driven-development-policy.md)'s different-toolchain exception, which is the only ground the role matrix allows. The application's behavior adapter is `@amiceli/vitest-cucumber` running under Vitest in jsdom; this adapter is `playwright-bdd` running under the Playwright runner against a downloaded Chromium binary, with its own generated test directory and its own browser-install step. Those two cannot share a runner, so co-location is not available. It owns no separate corpus, no unit layer, and no numeric coverage gate, as the same matrix requires.

### The E2E Project's Target Contract

`apps/wahidyankf-www-e2e` gets its own table rather than sharing the one above, because it exposes a different set of names and none of the application's coverage targets. It owns seven targets in total: the five `delivery.md` authors when it creates `project.json`, plus the two children the `lint` aggregate invokes.

| Target | Command shape | `cwd` | Cached | `outputs` |
| --- | --- | --- | --- | --- |
| `install` | `npx playwright install --with-deps chromium` | `{projectRoot}` | no | none |
| `typecheck` | `tsc --noEmit` | `{projectRoot}` | yes | none |
| `lint` | ordered aggregate of `lint:biome` then `lint:commentary` | none | yes | none |
| `lint:biome` | `biome check` | `{projectRoot}` | yes | none |
| `lint:commentary` | `eslint --config eslint.config.mjs steps` | `{projectRoot}` | yes | none |
| `test:e2e` | the unconditional-`test.skip` guard, then `npx bddgen && npx playwright test` | `{projectRoot}` | no | none |
| `specs:e2e:baseline` | `npx bddgen`, then the `test.fixme` recount against `e2e-skip-baseline.json` | `{projectRoot}` | yes | none |

The `test:e2e` command is a reduction of the source target rather than an invention. At the recorded source commit that target ran the same guard and then `node scripts/run-docker-e2e.mjs`, and the only two commands that runner issues once its Docker work is done are `npx bddgen` and then `npx playwright test`, both from the project directory. It also forwards its own extra arguments and sets `BASE_URL` from the published container port; neither survives, because no container is started and the `webServer` block supplies the base URL. This plan drops the Docker build, the container health wait, and the published-port lookup, because `playwright.config.ts` gains a `webServer` block running `npx nx run wahidyankf-www:start` instead; what is left is the two commands above. `delivery.md` writes the guard verbatim, so the table states its shape rather than repeating it.

`install` and `test:e2e` are the two uncached targets. `install` writes browsers into Playwright's own cache outside the workspace, so there is no `outputs` path Nx could restore and a replay would report success on a machine holding no browser. `test:e2e` starts a real server and drives a real browser, and the Phase 5 gate runs it again immediately after the Phase 5 item that runs it cold, so a cache hit there would replay a result instead of verifying one — the same reason the application's `test:integration` and `static-routes:validation` are uncached. Its `test-results/` and `playwright-report/` directories are therefore not declared as `outputs`; the root `.gitignore` rules Phase 1 adds are what keep them out of `git status --short` and out of `prettier --check .`.

`typecheck` and `lint` take their `cache` setting from the root `nx.json` `targetDefaults`, which names those two among its six. `install`, `lint:biome`, `lint:commentary`, `test:e2e`, and `specs:e2e:baseline` are not among those six, so each declares `cache` explicitly, exactly as the application's `project.json` does for the targets `targetDefaults` does not reach.

`specs:e2e:baseline` is cached and declares no `outputs`, which is safe only because nothing downstream reads what it writes: `npx bddgen` regenerates `.features-gen/`, and `test:e2e` runs its own `npx bddgen` rather than consuming this target's. That is the same reasoning `typecheck` uses above for its `tsconfig.tsbuildinfo`, and it is why the `outputs` trap the application table describes does not apply here.

## Coverage Denominators

`test:coverage:unit` covers `src/**` and enforces a 99% line threshold, matching how `badakmini-cli` states its statement floor. That denominator is not what arrives: the ported `vitest.config.ts` sets no `coverage.include`, so only files some test imports appear at all. Phase 3 sets `coverage.include: ["src/**"]` explicitly, which is what makes an untested module count against the gate instead of vanishing from it. Nothing is set beside it: Vitest 4 has no `coverage.all` option — `BaseCoverageOptions` at the pinned `4.1.0` carries no such key — and because the application's `typecheck` covers `vitest.config.ts`, writing one would fail `tsc --noEmit` as an excess property.

Three source exclusions also arrive and are deleted rather than kept: `src/app/layout.tsx`, `src/app/head.tsx`, and `src/features/cv/core/data.ts`. All three are runtime code, and omitting runtime code from the denominator is one of the four things the testing policy names by name. `src/app/fonts/**`, `src/app/**/*.css`, `src/test/**`, `**/*.config.*`, `**/.next/**`, `**/dist/**`, and `**/coverage/**` stay excluded: they are assets, fixtures, and build output rather than code under test. The build scripts under `apps/wahidyankf-www/scripts/` sit outside `src/` and so outside the denominator; `generate-cv-pdf.ts` is proved by the Phase 4 run that regenerates the published PDF, and `validate-static-routes.mjs` by `static-routes:validation`.

The ported configuration also carries a `coverage.thresholds` block of `lines: 80`, `functions: 80`, `branches: 75`, `statements: 80`. It is deleted, not raised. The threshold this repository enforces is the `--coverage.thresholds.lines=99` flag on the target, and the testing policy forbids duplicating an executable threshold as metadata, where the two can silently disagree and the lower one is the one a reader believes.

`test:coverage:integration` covers only `src/features/cv/core/pdf.ts` and `src/features/cv/shell/pdf.ts`, the modules that actually touch the filesystem, because a denominator padded with unreachable modules turns a 99% gate into a rounding exercise. That narrowing has to ride on the target command rather than on a project entry in `vitest.config.ts`: in Vitest 4 `coverage` is a root-level option a project config cannot set — `ProjectConfig` omits it — so the `coverage.include: ["src/**"]` above governs the `integration` project too. The target therefore carries `--coverage.include='src/features/cv/**/pdf.ts'`, which replaces the configured include rather than adding to it and leaves exactly those two modules in the denominator. Without that flag the integration run measures all of `src/**` with two PDF tests executing, and the 99% threshold cannot be reached.

If a module cannot reach the floor, the resolution is a test, not an exclusion. The testing policy forbids broad exclusions and forbids lowering the threshold, and permits a generated-code exclusion only with the owner's explicit approval and a written reason.

## Toolchain Conformance and Its Fallback

[Testing tooling](../../../../repo-governance/development/testing-policy/tooling.md) names three components for a TypeScript project — "TypeScript 6's `tsc --noEmit`, Biome, and project-local ESLint commentary checks" — and the [code commentary policy](../../../../repo-governance/development/code-commentary-policy.md) names the third precisely: "TypeScript uses ESLint and `eslint-plugin-jsdoc` to require complete-sentence summaries for named executable declarations." The target state is therefore all three plus every dependency exact-pinned, and `[AC-9]` is judged against all three.

Biome replaces oxlint as the linter and only as the linter. Prettier remains the formatting source of truth, as the [code style policy](../../../../repo-governance/development/code-style-policy.md) states, so the root `biome.json` sets `formatter.enabled` and `assist.enabled` to `false` and `lint:biome` runs `biome check` as a lint pass. The two cannot both be enabled here: Biome v2 defaults `formatter.indentStyle` to tab, while Prettier in this repository uses two spaces — `.prettierrc.json` sets only `proseWrap`, leaving Prettier's `useTabs: false` and `tabWidth: 2` defaults in force. An enabled Biome formatter would therefore fail `lint` on every ported file, and a `biome check --write` run to "fix" that would retab those files and break `npm run format:check` for the whole repository. Disabling the assist actions closes the same conflict over import ordering.

Prettier's own configuration differs on the two sides, which is why conforming to this repository's is a named step of the port rather than an afterthought. `ose-public/.prettierrc.json` sets `printWidth: 120`, sets `proseWrap: "preserve"`, and loads `prettier-plugin-tailwindcss`, which reorders Tailwind class lists; this repository's `.prettierrc.json` sets `proseWrap: "never"` and nothing else, leaving Prettier's `printWidth: 80` default in force and loading no plugin. Ported files therefore arrive failing this repository's format gate. Checked at the recorded source commit with this repository's configuration, 38 of the 58 Prettier-parseable tracked files under `ose-public/apps/wahidyankf-www` fail `prettier --check`, as do 11 of the 15 under `ose-public/apps/wahidyankf-www-fe-e2e` and `ose-public/scripts/next-with-port.mjs`. `npx prettier --check .` passes in this repository today, so the port is what creates the failure, and the plan closes it where it creates it: Phases 1, 3, 5, and 6 each carry an explicit `npm run format` item, placed after that phase's copying and before its gate, with `npm run format:check` exiting 0 as the acceptance.

That reformat is a formatting change and not a content change. It moves line breaks, quoting, and Tailwind class order; it changes no identifier, no string literal, no comment sentence, and no behavior. A later reader diffing a ported file against its `ose-public` original will see it and should expect it rather than read it as drift. The alternative was to exempt `apps/wahidyankf-www/**` and the E2E project through an ignore file, and it is deliberately not taken: that would put the two newest projects outside the formatting source of truth the [code style policy](../../../../repo-governance/development/code-style-policy.md) names, and [file impact](file-impact.md) already rules out introducing a root `.prettierignore` at all.

Neither `eslint` nor `eslint-plugin-jsdoc` arrives with the ported manifests, which used oxlint alone. Both are added at the root in Phase 1 beside `typescript` and `@biomejs/biome`, and the application's `lint` target becomes an ordered aggregate: `lint:biome` first, then `lint:commentary`. The [Nx workspace policy](../../../../repo-governance/development/nx-workspace-policy.md) requires exactly that shape for a target that must run several commands in order — an `nx:run-commands` block with an explicit `options.commands` list, `parallel` set to `false`, and each entry invoking an existing target entry point rather than copying its command.

Six specifiers arrive with caret ranges and are pinned in Scaffold: `class-variance-authority`, `clsx`, `react-icons`, `tailwind-merge`, and `@vitejs/plugin-react` in the application manifest, and `@vitejs/plugin-react` again in the E2E manifest, which the application-side pinning does not reach. Three are then removed outright, by two separate acts in two phases. `class-variance-authority` and `react-icons` leave the application manifest through the unused-importer item later in Phase 3, that item's removal branch firing because neither has an importer. `@vitejs/plugin-react` leaves the E2E manifest in Phase 5 instead: the Phase 3 item reaches the application manifest only, and this project's adapter is the Playwright runner rather than Vitest, so nothing here imports a Vite plugin. The application manifest keeps its own copy, which is why the two removals could not be one item. All three are therefore pinned only for the interval in which they exist here; `clsx`, `tailwind-merge`, and `@vitejs/plugin-react` stay pinned in the application manifest.

Both ported manifests also carry `"typescript": "5.8.3"` in their own `devDependencies`. Both entries are deleted, so the root pin is the only TypeScript in the tree. This is not tidying: under npm workspaces a nested pin resolves ahead of the root one, so leaving either in place would let the root show TypeScript 6 while the project it governs still compiled on 5.8.3 — `[AC-9]` would report conformance the build did not have.

The fallback is per-component, by owner direction, and now covers three components rather than two. If TypeScript 6 fails against Next 16 or React 19, keep Biome and ESLint and pin TypeScript at the highest version that type-checks clean. If Biome fails, keep TypeScript 6 and ESLint and retain oxlint. If ESLint or `eslint-plugin-jsdoc` cannot run against these sources, keep the other two and record the commentary check as the component that could not conform. Each retreat is recorded twice: as a dated entry in `learnings.md` naming the exact error, and as an amendment to `testing-policy/tooling.md` stating the deviation and its evidence. A deviation that lives only in a commit message is the outcome this plan exists to prevent.

One deviation is known in advance rather than discovered, and it is named here so it is not mistaken for an oversight. The [code style policy](../../../../repo-governance/development/code-style-policy.md) sets the language target as "strict TypeScript with CommonJS-compatible Node output", which is what `tsconfig.base.json` encodes with `module` and `moduleResolution` at `NodeNext` and `target` at `ES2024`. The application cannot inherit those: it arrives with `module: esnext`, `moduleResolution: bundler`, `target: ES2017`, `jsx: react-jsx`, and the `next` TypeScript plugin, which is the configuration Next 16 compiles against. The E2E project arrives with `module: esnext`, `moduleResolution: bundler`, and `target: ES2022`, and this plan keeps those values. It does not keep the ported file's lack of an `extends`: Phase 5 points it at `tsconfig.base.json` so both projects reach the shared base the same way, each overriding exactly those three options on top of it. Two TypeScript projects inheriting by different routes is a difference nobody could justify later, and the deviation worth recording is the three options, not one project standing outside the base. Both keep `strict` true. That is a deviation from the language-target sentence, not from the strictness requirement, and it takes the same record as any toolchain retreat: a dated `learnings.md` entry and an amendment to `testing-policy/tooling.md` naming the deviation and why a bundler-targeted framework cannot emit CommonJS-compatible Node output. `tsconfig.base.json` itself stays untouched, because `badakmini-cli` is Go and no other project would benefit from loosening the shared base.

## Deployment

`vercel.json` is ported with its configuration unchanged, including its root-prefixed install command — which resolves correctly because the Vercel project root is the app directory — and its `ignoreCommand`, which gates every build on the branch named `prod-wahidyankf-www`. Its bytes do change, because the source is written at `ose-public`'s `printWidth: 120` and fails `prettier --check` here. Phase 6 records the source SHA-256 into `evidence/vercel-json-digest.txt` while the copy is still byte-identical, then reformats it and proves by parsed-JSON equality that every key survived. That digest is the provenance record a later `shasum` against the delivered file can no longer supply.

That branch gate is the problem this plan closes rather than imports. The [plans organization policy](../../../../repo-governance/conventions/plans-organization-policy.md) states that delivery goes directly to `main` with no pull-request flow and no worktrees, so a long-lived `prod-*` branch appears nowhere in this repository's rules. An undocumented branch in a repository whose stated model is main-only is exactly what a later cleanup pass deletes as dead. Phase 6 adds a short deployment rule under `repo-governance/development/` stating that `main` is the delivery target and that `prod-<project>` is a promotion pointer no plan advances automatically.

No branch is created and no deploy is triggered by this plan. The configuration lands dormant.

## Risks

- Phase 3 is large by construction, because no gate may close below 99%. Its checklist is ordered feature area by feature area so that a failure localizes even though the phase does not.
- `static-routes:validation` inside `test:quick` makes every affected push run an uncached Next production build. Accepted by owner direction; its wall-clock cost is measured and recorded in Phase 3 so a later reversal has evidence.
- Playwright adds a browser download to continuous integration. `full-bdd.yml` gains an install step, and `check:workflows` validates the result.
- The E2E adapter's `missingSteps: "skip-scenario"` renders an unbound scenario as `test.fixme` and lets the suite exit 0. `ose-public` caught a regression here with `specs:e2e:coverage`, which does not come. Phase 5 replaces the one check that target provided: the four unbound features and their nineteen scenarios are recorded in `apps/wahidyankf-www-e2e/README.md` for a reader, the count is recorded as a single integer in the tracked `apps/wahidyankf-www-e2e/e2e-skip-baseline.json`, and a `specs:e2e:baseline` target reruns `npx bddgen`, recounts the generated `test.fixme` entries, and exits non-zero when the two disagree. That integer counts generated tests rather than scenarios: `playwright-bdd` generates one test per `Examples` row and marks each one, so the four Scenario Outlines among those features push the recorded number well above nineteen. Without it, deleting a step file would look like a passing run.
- Deleting `cv/` may break a reference held in a harness prompt or a governance document. Phase 4 searches for references before deleting, not after.

## Rollback

A phase lands as a thematic commit series on `main`, not as one commit: the [thematic commits policy](../../../../repo-governance/conventions/thematic-commits-policy.md) gives each commit one purpose, so a phase that ports code, edits governance, and records itself lands as three. Reverting a phase therefore means reverting its series, and the revert point that matters is the commit carrying the destructive or irreversible change rather than the most recent one. For the only destructive change in this plan, deleting `cv/`, that commit is `31aabe5`; reverting it restores all seven files intact, which the Phase 4 gate rehearsed and proved by digest before the deletion was pushed. Phase 4 is the only phase that deletes existing repository content, so its commit is the single revert point that restores `cv/` intact.
